# الشاشة 32 — إدارة المؤسسات المستفيدة (Organizations Management)

**المسار:** `/platform/organizations`  
**مجموعة الواجهات:** إدارة المنصة  
**الدور:** مسؤول المنصة `platform_admin`، صلاحية المعاينة `platform.manage`.  
**حالة التنفيذ:** واجهة Next.js تفاعلية للعرض فقط، غير متصلة بخادم FastAPI، وليست إدارة مستأجرين إنتاجية.  
**الحالة الوظيفية:** UC-07 — إدارة/تهيئة المؤسسات؛ لم تتحدد جميع مسارات API النهائية في Backend.

## الهدف

تعريف المسؤول التشغيلي بالمؤسسات المسجلة على المنصة من حيث الحالة العامة وخدمات المنصة ومراحل التهيئة، **بدون** إتاحة استعراض محتويات قواعد البيانات المؤسسية أو بيانات المستخدمين أو الوثائق أو أسرار الاتصال. تعكس الشاشة تصميم بيان المعتمد، وتُظهر فقط **8 مؤسسات اصطناعية** بعناوين وأسماء افتراضية.

## عناصر الواجهة

1. **ترويسة وبطاقات KPIs:** الإجمالي والنشطة وقيد التهيئة والموقوفة.
2. **مرشحات:** نص البحث بالعربية (يدعم صور الألف والتشكيل)، الحالة، نوع المؤسسة، الخدمة، والترتيب.
3. **قائمة المؤسسات:** الاسم التجريبي، المعرّف، المنطقة الوصفية، الحالة، حالة التهيئة، الخدمات المختصرة، وآخر نشاط توضيحي.
4. **الصفحات:** 6 مؤسسات في الصفحة الواحدة، مع السابق/التالي.
5. **درج التفاصيل:** المعرف، الرمز، القطاع، المنطقة، الحالة، الخدمة، وصف افتراضي، ملاحظة عزل المستأجرين.
6. **إجراءات معاينة:** محاكاة إيقاف أو تنشيط المؤسسات الموجودة بواجهة تأكيد، باستثناء المؤسسات قيد التهيئة.
7. **حفظ العرض:** الحالة فقط في `localStorage` ضمن مفتاح تجريبي ثابت؛ لا تخزين بيانات اعتماد أو معلومات مستخدمين.
8. **تصدير CSV:** بيانات تعريفية اصطناعية للنتائج المصفّاة، مع معالجة خطر صيغة جداول البيانات (CSV injection).
9. **صلاحيات:** يمكن اختيار دور آخر لتجربة رسالة رفض الوصول؛ لا يفرض ذلك RBAC الحقيقي.
10. **التنقل:** روابط تنقل من داخل الصفحة دون تغيير الشريط الجانبي المرجعي، ورابط إلى معالج التهيئة `/platform/onboarding` الموجود في الكتالوج.

## سيناريوهات التجربة

| العملية | النتيجة المتوقعة |
|---|---|
| فتح `/platform/organizations` | تظهر ثماني مؤسسات تدريبية وخيارات التصفية |
| البحث عن «جامعة» | تظهر مؤسستان افتراضيتان |
| التصفية بالحالة «موقوفة» | تظهر مؤسستان عند بدء الحالة الافتراضية |
| فتح «جامعة الأفق التجريبية» | تفاصيل تشغيلية فقط، دون بيانات داخلية |
| اختيار «إيقاف تجريبي» | تأكيد ثم تحديث محلي للحالة دون API |
| تحديث الصفحة | تُقرأ الحالات التجريبية المسموحة المخزنة محليًا |
| اختيار موظف المؤسسة في محدد الدور | منع عرض قائمة المؤسسات |
| اختيار «قيد التهيئة» | لا يظهر زر تغيير الحالة يدويًا |
| تصدير CSV | ملف تجريبي يحوي معلومات وصفية فقط |

## الضوابط الأمنية المقترحة للإنتاج

- مصادقة قوية ومسارات Backend تتحقق من `platform.manage` حسب المؤسسة ودور المشغل.
- فصل واجهة مشغل المنصة عن الإدارة الداخلية للمؤسسات؛ `platform_admin` لا يرث `users.manage` أو `sources.manage` أو الوصول إلى محتوى `documents.search` الخاص بمؤسسة.
- واجهة المشغل ترى معلومات تشغيلية *متفقًا عليها ومصرحًا بها فقط*، ولا تتصل مباشرةً بقواعد بيانات المؤسسات.
- إجراءات الإيقاف/التنشيط الحقيقية تتطلب تدفق موافقة، وحماية ضد الإعادة، وتوثيق تدقيق غير قابل للعبث، وأسباب القرار، وضوابط عزل tenant.
- منع وصول أسرار الاتصال وحقول PII والبيانات الأكاديمية أو مستندات المؤسسات إلى React Client Components أو ملفات التصدير.
- عدم الوثوق بحماية واجهة React أو localStorage؛ فرض السياسات يجب أن يتم في FastAPI والطبقات الأدنى.

## عقود REST المقترحة لاحقًا — غير منفذة

| الطلب | المسار التوضيحي | الهدف |
|---|---|---|
| GET | `/api/v1/platform/organizations` | قائمة metadata مخصصة لمشغل المنصة |
| GET | `/api/v1/platform/organizations/{id}` | تفاصيل تشغيلية محدودة ومصرح بها |
| POST | `/api/v1/platform/organizations/{id}/status-requests` | إنشاء طلب تغيير حالة يخضع لتدقيق وموافقة |
| GET | `/api/v1/platform/organizations/{id}/onboarding-status` | حالة التهيئة دون تسريب بيانات المصدر |

> هذه عقود تصميم مقترحة، لا مسارات مثبتة في Backend. يتم تثبيتها لاحقًا وفق الشفرة الفعلية ومتطلبات التفويض.
