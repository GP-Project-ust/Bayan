# الشاشة 21 — إدارة الأدوار والصلاحيات (Roles & Permissions)

## 1. الهدف

مسار الصفحة: `/admin/roles`. تعرض هذه الشاشة **الأدوار الأربعة لمشروع بيان** ومصفوفة صلاحيات `RBAC` المستخدمة في نماذج الواجهات، مع تمييز صلاحيات مسؤول المنصة عن إدارة بيانات المؤسسة، وفق مبدأ أقل امتياز.

> حالة التنفيذ: **نموذج واجهة متفاعل محلي**. لا يتم تعديل السياسة المركزية `lib/access/policy.ts`، ولا إرسال الطلبات إلى FastAPI، ولا منح صلاحيات فعليًا. ليست هذه الشاشة مراجعة أمنية رسمية.

## 2. عناصر الواجهة

| العنصر | الوصف |
|---|---|
| مسار التنقل | العودة إلى لوحة الإدارة وإدارة المستخدمين |
| محدد الدور التجريبي | تغيير دور الممثل لأغراض اختبار صلاحية الوصول للصفحة فقط |
| بطاقات ملخصة | عدد الأدوار، وعدد العمليات، وصلاحيات الدور المختار، والمسودات المحلية |
| بطاقات الأدوار | الموظف، المدير، مسؤول تقنية المعلومات، مسؤول المنصة |
| مصفوفة الصلاحيات | 16 صلاحية × 4 أدوار، مجمعة حسب الوظيفة |
| البحث والتصفية | حسب اسم العملية أو رمزها أو المجموعة |
| درج تفاصيل الدور | النطاق والوصف والصلاحيات المسموحة |
| مقارنة الأدوار | الحقوق المشتركة والمضافة والمحذوفة بين دورين |
| طلب مراجعة | اقتراح منح/سحب حق مؤسسي مع ذكر السبب؛ **مسودة محلية فقط** |
| تأكيد مسح المسودات | نافذة `Dialog` مع تأكيد |
| الحالات | منع وصول، نتائج فارغة، فشل التخزين، رفض طلب غير صحيح |

## 3. الأدوار المعتمدة

- `employee`: موظف المؤسسة؛ الاستعلامات والبحث والمصادر وعرض التقارير المصرح بها.
- `manager`: مدير المؤسسة؛ الاستعلامات والتقارير والإنشاء والتصدير والتحليلات.
- `it_admin`: مسؤول تقنية المعلومات؛ الإدارة المؤسسية والعروض الذكية وسجل التدقيق وتتبع الوكلاء وفحص SQL المصرح به.
- `platform_admin`: مسؤول المنصة؛ عمليات المنصة والتهيئة فقط، **دون وراثة صلاحيات بيانات المؤسسة**.

مصدر السياسة المرجعي للواجهة: `lib/access/policy.ts`، ويجب الرجوع إليه عند إضافة عمليات جديدة، وعدم افتراض أي أذونات لم يذكرها.

## 4. قواعد المراجعة التجريبية

1. فتح المراجعة متاح فقط عند اختيار ممثل له `roles.manage` في المحاكاة.
2. هدف المراجعة لا يجوز أن يكون `platform_admin`، ولا يجوز طلب `platform.manage` أو `onboarding.run` من هذه الشاشة.
3. طلب المنح يرفض إذا كانت الصلاحية ممنوحة أصلًا؛ وطلب السحب يرفض إذا لم تكن ممنوحة.
4. يلزم سبب بين 12 و500 حرف، ومنع الطلبات المكررة، والحد الأقصى 50 مسودة.
5. تستخدم المسودات التخزين المحلي `localStorage` بالمفتاح `bayan.demo.role.review.v1`، مع التحقق الصارم من المخزون المستعاد.
6. حذف المسودة ومسحها لا يغيّران سياسة النظام، كما أن إنشاء المسودة **لا يغيّر** أذونات أي شاشة ولا أي مستخدم.
7. لا يتم عرض سجلات المؤسسة الخاصة بمسؤول المنصة على أنها حسابات مؤسسية؛ العدد الخاص به غير ممثل في بيانات العرض.

## 5. التكامل مع الشاشات السابقة

- المسار `/admin/users` يحتوي أصلًا على رابط «استعراض مصفوفة الأدوار».
- أُضيف رابط «الأدوار والصلاحيات» إلى القائمة الجانبية لقسم الإدارة، باستخدام فئة التنسيق الأصلية دون تغيير ألوانها.
- لم تُعدل شاشة المحادثة أو لوحة الإدارة المرجعيتان، ولا ملفات الصورة أو سياسة الأدوار المركزية.
- تعتمد الأعداد التجريبية للأدوار على قائمة المستخدمين المخزنة محليًا والتي تستخدمها الشاشات 18–20؛ ولا تمنح تلك القائمة حقًا فعليًا.

## 6. متطلبات الربط الحقيقي لاحقًا

قبل استخدام الصلاحيات في الإنتاج، يجب توفير هوية مستخدم موثقة من Backend وربط كل حساب بالمؤسسة، والتحقق من صلاحيات API على الخادم في كل طلب، وتطبيق الفصل بين المؤسسات، وسياسات إتاحة المصادر والجداول والوثائق، وسجل تدقيق غير قابل للتلاعب. لتفعيل مراجعة الصلاحيات مستقبلاً يلزم تصميم طلب رسمي وموافقة مخولة مع حوكمة تغيير، بدل اعتماد المسودات المحلية.

**لا توجد نقطة نهاية API مثبتة في المشروع لهذه المراجعة؛ لذا لم نخترع عنوان Endpoint.**

## 7. الاختبارات

- اختبارات العقود: `npm run check:roles`.
- اختبار المتصفح (بعد تثبيت الحزم): `npx playwright test tests/e2e/roles-permissions.spec.ts`.
- الاختبارات تشمل العزل بين المنصة والمؤسسة، وتناسق مقارنة الصلاحيات، ورفض المنح غير المسموح، وعدم تغيير المصفوفة الأصلية، وأخطاء بيانات التخزين المحلي.
- اختبار البناء الكامل: `npm run build` بعد تشغيل `npm install` على بيئة تطوير تتيح تنزيل الحزم.

## 8. معايير القبول

- تظهر أربعة أدوار و16 عملية، مع توضيح المسموح وغير المسموح.
- تعمل الفلاتر والمقارنة والتفاصيل على الشاشات المختلفة باتجاه RTL.
- لا يعرض الدور غير المخول إدارة الأدوار.
- يمنع منح أدوار المنصة من الإدارة المؤسسية.
- لا يغيّر إرسال المراجعة أي إذن فعلي، ويُذكر ذلك في الواجهة والتوثيق.
- تبقى المكونات والألوان متوافقة مع Design System الأصلي.
