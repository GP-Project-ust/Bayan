# الشاشة 18 — إدارة مستخدمي المؤسسة | Bayan

## الهدف
تفعيل المسار `/admin/users` كشاشة إدارية عربية مستقلة ومتجاوبة، مع الالتزام بمرجع التصميم الكحلي/التركوازي. تخدم المتطلبات المقترحة `UC-04` و`FR-02` وتستخدم دور مسؤول تقنية المعلومات في محاكاة صلاحيات العرض.

## ما أُنجز
- قائمة بيانات **14 مستخدمًا خياليًا** من مؤسسة وهمية واحدة، وحالتان (نشط/معطّل) وثلاثة أدوار مؤسسية (موظف، مدير، مسؤول تقنية معلومات).
- أربع بطاقات لعدد الحسابات والنشطة والمعطلة ومسؤولي تقنية المعلومات النشطين.
- البحث العربي بترجمة بسيطة للاختلافات الإملائية، والتصفية حسب الدور والحالة والقسم، والترتيب والتصفح مع ثمانية سجلات في الصفحة.
- **نافذة إضافة** مع فحص الاسم والبريد والتكرار والقسم والدور، وتحديث البيانات محليًا.
- **درج تفاصيل** مستقل للمستخدم، و**درج تعديل** الحقول والدور، ونافذتا تأكيد للتعطيل/التنشيط واستعادة بيانات العرض.
- حماية محاكاة لمنع تعطيل الحساب الإداري الحالي أو سحب دوره، وكذلك منع تعطيل/إزالة دور آخر مسؤول تقنية معلومات نشط.
- تخزين محلي اختياري `bayan.demo.users.v1` مع التحقق من سلامة السجلات عند إعادة القراءة. ليست هذه جلسة مستخدم أو مخزنًا آمنًا.
- ربط مع الشريط الجانبي الإداري الأصلي دون تغيير تنسيقه، مع رابط من الشاشة إلى صفحة `/admin/roles` المخططة للمستقبل.
- دعم RTL والنوافذ، والجدول القابل للتمرير أفقيًا على الهاتف، وتسميات أدوات الإدخال والأزرار.

## الأدوار والسياسات
- `it_admin`: يسمح له في **المعاينة فقط** بعرض الشاشة وإجراء التغييرات المحلية.
- `manager`, `employee`, `platform_admin`: تعرض الشاشة حالة رفض وصول تجريبية. مسؤول المنصة ليس تلقائيًا مديرًا لحسابات المؤسسة.
- لا يمكن إسناد دور مسؤول المنصة داخل نموذج حسابات المؤسسة.
- قاعدة البيانات وFastAPI وحدهما مسؤولان عن التحقق الفعلي من الهوية والمؤسسة وصلاحيات RBAC، ومنع التحايل والتغييرات المتزامنة.

## الحدود المهمة
جميع الأسماء والبريد والمعلومات أمثلة خيالية (`@example.test`). لا يُنشأ حساب، ولا يُرسل بريد أو دعوة، ولا يُفعّل أو يُعطّل حساب حقيقي، ولا يُكتب سجل تدقيق رسمي. نشاط التعديلات المعروض هو سجل محلي مؤقت للجلسة. يلزم ربط API حقيقي بعد مراجعة عقود الخادم ومخطط قاعدة البيانات.

## API مقترحة مستقبلًا — ليست منفذة
- `GET /api/v1/institution/users` جلب المستخدمين مع الفلاتر والصفحات وسياق المؤسسة من الجلسة الموثقة.
- `POST /api/v1/institution/users` إنشاء حساب وإرسال دعوة عند تفعيل الخدمة.
- `PATCH /api/v1/institution/users/{id}` تعديل الحقول المسموحة والدور وفق سياسة RBAC، مع تدقيق.
- `PATCH /api/v1/institution/users/{id}/status` تغيير حالة الحساب بعد ضوابط آخر مسؤول وإبطال الجلسات عند الحاجة.
- `GET /api/v1/institution/users/{id}` تفاصيل حساب داخل المؤسسة فقط.

المسارات أعلاه **مقترحات تصميم وليست تأكيدًا لمسارات موجودة**؛ المسارات الفعلية تُحدد مع فريق Backend.

## اختبار الشاشة
1. افتح `http://localhost:3000/admin/users` بعد `npm install && npm run dev`.
2. جرّب البحث بالعربية والمرشحات والصفحات، ثم إضافة اسم وبريد افتراضيين.
3. جرّب إدخال بريد مستخدم موجود والتحقق من رسالة منع التكرار.
4. راجع درج التفاصيل والتعديل والتعطيل ثم استعادة بيانات العرض.
5. جرّب دور الموظف ومدير المؤسسة ومسؤول المنصة في المحدد؛ يجب إخفاء الإدارة ومنع إجراء تغييرات من واجهة النموذج.
6. جرّب عرض 390 و768 و1280 بكسل، وإمكانية الوصول بالنقر على Tab وزر Escape في النوافذ.
7. شغّل `npm run check:users` و`npm run check:outliers` و`npm run lint` و`npm run build` و`npm run test:e2e` بعد توفر dependencies.
