# الشاشة 28 — سجل التدقيق | BAYAN

## الحالة والمسار

- مسار Next.js: `/admin/audit`.
- حالة التنفيذ: **واجهة أمامية تجريبية** فقط؛ ليست نظام سجل تدقيق حي.
- المرجع الوظيفي: UC-06 (مراجعة سجل التدقيق وتتبع التنفيذ) ضمن وثيقة المشروع، وكتالوج الشاشات.
- الألوان: الكحلي `#0A2342` والتركوازي `#00A6B2` والخلفية البيضاء / الفاتحة، مع العربية وRTL.
- الهيكل المعاد استخدامه: `AdminLayout`، و`DemoAccessProvider`، و`Drawer`، و`Button`، و`Toast`، و`StatePanel`.

## مكونات الشاشة

1. عنوان وبطاقات لإجمالي الأحداث والعمليات الناجحة والمرفوضة والفاشلة.
2. بحث عربي يتعامل مع بعض اختلافات التشكيل والهمزات، وتصفية بحسب الفئة والنتيجة والفاعل وفترة التاريخ.
3. جدول للقراءة فقط يعرض التاريخ، الفاعل، نوع العملية، الإجراء، المورد الوصفي، النتيجة، ومعرّف التتبع؛ وترقيم صفحات (7 أحداث لكل صفحة).
4. درج جانبي يعرض البيانات الوصفية للحدث ومعرّف التتبع ونسخه، مع تنبيه يتعلق بإخفاء المحتوى الحساس.
5. تنزيل CSV محليًا للأحداث المصفاة *فقط*، مع BOM لدعم UTF-8 وحماية القيم النصية من حقن صيغ جداول البيانات.
6. حالة منع وصول وحالة لا نتائج وحالة خطأ نطاق تاريخ معكوس.

## البيانات وحدود الخصوصية

- يحتوي `lib/audit/events.ts` على **18 حدثًا اصطناعيًا ثابتًا** بصيغة `AUD-DEMO-xxx`؛ التواريخ والفاعلون والإجراءات تجريبية.
- لا يفتح التطبيق اتصالًا بشبكة، ولا يقرأ `localStorage` أو سجلًا من أي صفحة أخرى، ولا يعد الأحداث الموجودة في تلك الصفحات سجلًا موثوقًا.
- لا تتضمن أحداث العرض كلمات مرور أو رموز جلسات أو نص SQL المنفذ أو أسئلة المستخدم الخام أو بيانات المؤسسة الفعلية.
- الفاعلون مجرد تسميات أدوار تجريبية، ومعرّفات التتبع اصطناعية.
- لا يوجد تعديل/حذف لأي حدث؛ سجل التدقيق الحقيقي يجب أن يكون غير قابل للتلاعب من الواجهة.

## صلاحيات واجهة المستخدم التجريبية

- المعاينة متاحة لدور `it_admin` من خلال `audit.view` في `lib/access/policy.ts`.
- مدير المؤسسة، والموظف، ومسؤول المنصة **لا يرثون قراءة سجل هذه المؤسسة** تلقائيًا.
- هذا **إخفاء واجهة فقط**؛ كل GET أو EXPORT حقيقي يجب أن يتحقق من الهوية والدور والمؤسسة داخل الخادم.
- إدارة سجلات المنصة وقواعد الاحتفاظ وإثبات سلامة الأحداث تتطلب تصميم Backend منفصلًا.

## عقود API المقترحة مستقبلًا — ليست منفذة

| الطريقة والمسار المقترح | الغرض | الضوابط المطلوبة |
|---|---|---|
| `GET /api/audit/events` | استرجاع أحداث مصفاة ومرقّمة | هوية موثقة، صلاحية `audit.view`، عزل المؤسسة، حد أقصى للصفحة |
| `GET /api/audit/events/{event_id}` | تفاصيل حدث واحد | التحقق من وجود الحدث ضمن نطاق المؤسسة، الإخفاء ومنع التسريب |
| `GET /api/audit/events/export` | تصدير مجموعة مصرح بها | صلاحية تصدير منفصلة أو موافقة، تحديد نطاق التاريخ، سياسة احتفاظ ومراجعة التصدير |

**اقتراح هندسي وليس تنفيذًا حاليًا**: كل عملية حساسة في FastAPI تسجل حدثًا موحدًا يحتوي `event_id`, `occurred_at`, `tenant_id`, `actor_id`, `action`, `resource_type`, `resource_id`, `result`, `correlation_id` والحد الأدنى من البيانات الوصفية. ينبغي عدم كتابة الأسرار/النصوص الخام، وتطبيق صلاحية القراءة وعزل المؤسسة قبل الرد، وسياسة احتفاظ وسجل يصعب العبث به وضوابط rate limits للتصدير.

## سيناريوهات اختبار القبول

- `AUD-01`: يستطيع مسؤول تقنية المعلومات رؤية الأحداث والبطاقات.
- `AUD-02`: يرى المستخدم غير المخوّل رسالة رفض دون عرض جدول أو إمكانية التصدير.
- `AUD-03`: تصفية الأحداث بالفئة أو النتيجة أو الفاعل والنطاق الزمني بصورة متقاطعة.
- `AUD-04`: فحص فترة البداية بعد النهاية لا يعرض سجلات.
- `AUD-05`: فتح تفاصيل حدث ونسخ معرّف التتبع؛ لا تظهر أسرار.
- `AUD-06`: تصدير CSV محلي يقتصر على نتائج المرشحات ولا يتضمن بيانات غير ضرورية.
- `AUD-07`: تعطيل زر التصدير عند خلو النتائج.
- `AUD-08`: تدعم الصفحة الأبعاد 390 و768 و1280 بكسل، مع تمرير الجدول داخل حاويته.
