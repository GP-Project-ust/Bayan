# الشاشة 19 — إضافة مستخدم جديد (Add User)

**المسار:** `/admin/users/new`  
**التصميم:** Bayan Design System v1 (كحلي `#0A2342`، تركوازي `#00A6B2`، RTL)  
**المتطلب:** UC-04 / إدارة المستخدمين والأدوار  
**الوضع:** نموذج واجهة تفاعلي تجريبي، غير متصل بالخادم.

## حدود التنفيذ

تتيح الشاشة إضافة **سجل وهمي محلي** ضمن نطاق مؤسسة تجريبية ثابتة؛ لا تُنشئ حسابًا في FastAPI، ولا ترسل رسالة بريد أو كلمة مرور، ولا تمنح أذونات حقيقية. يرجى استخدام أسماء وعناوين `example.test` وهمية فقط. يحفظ النموذج بيانات العرض في `localStorage` بالمفتاح `bayan.demo.users.v1` نفسه الذي تستخدمه شاشة 18، ولذلك تظهر الإضافات التجريبية عند الرجوع إلى `/admin/users`.

## التصميم ومسار الاستخدام

1. **البيانات الأساسية:** الاسم الكامل والبريد؛ فحص التنسيق والتكرار.
2. **المؤسسة والقسم والدور:** المؤسسة مقفلة ضمن نطاق المستأجر، اختيار قسم من القائمة وأحد ثلاثة أدوار مؤسسية. يقتصر دور مسؤول المنصة على إدارة المنصة ولا يمكن منحه من هذا النموذج.
3. **المراجعة:** ملخص جميع البيانات، وحالة الحساب التجريبية، ونافذة تأكيد، ثم حفظ محلي بعد إعادة فحص البريد.
4. **نتيجة العملية:** بطاقة نجاح تتضمن معرف المستخدم في النموذج ورابطًا لقائمة المستخدمين وزرًا لإضافة مستخدم آخر.
5. **حالات الاستثناء:** منع الدخول لغير مسؤول تقنية المعلومات، رفض الاسم والبريد غير الصالحين، البريد المكرر، فشل التخزين المحلي، وإظهار تأكيد الخروج عند وجود تغييرات.

### المكونات المعاد استخدامها

`AdminLayout`, `DemoAccessProvider`, `DemoRolePicker`, `StatePanel`, `Button`, `Dialog`, وعمليات `validateUserDraft`, `createUser`, `restoreUserFixtures` من `lib/user-management/users.ts`. جميع أنماط CSS الجديدة معزولة تحت `.banu`، بينما يبقى تصميم المحادثة ولوحة الإدارة الأصلي دون تعديل.

### صلاحيات المستخدمين

- `employee`: موظف المؤسسة؛ لا يفتح شاشة الإدارة.
- `manager`: مدير المؤسسة؛ لا يفتح شاشة إضافة المستخدم.
- `it_admin`: مسؤول تقنية المعلومات؛ يمكنه تشغيل النموذج التجريبي.
- `platform_admin`: مسؤول المنصة؛ لا يرث إدارة مستخدمي المؤسسة تلقائيًا.

> قيود React ليست آلية أمان: يحتاج تطبيق الإنتاج جلسة موثوقة، وسياسات RBAC مفروضة في API، وعزل المستأجرين، وسياسة تدقيق، وإجراءات دعوة وتفعيل آمنة، بالإضافة إلى منع التكرارات ضمن قاعدة البيانات نفسها.

## اتفاق API مقترح — غير منفذ

| طريقة | مسار تصميمي مقترح | الغرض |
|---|---|---|
| `GET` | `/api/v1/institutions/me/departments` | الأقسام المسموح للمسؤول استخدامها |
| `GET` | `/api/v1/institutions/me/roles` | الأدوار المسموح بتعيينها |
| `POST` | `/api/v1/institutions/me/users` | إنشاء الحساب بعد التحقق من الدور والمؤسسة والبريد |
| `POST` | `/api/v1/institutions/me/users/{id}/invitation` | إرسال دعوة آمنة عند تفعيل الميزة |

الاستجابات المقترحة تميز `400` مدخلات غير صالحة، `401` عدم مصادقة، `403` منع وصول، `409` بريد مكرر، `429` تجاوز حد، و`500` خطأ خادم، دون كشف معلومات حساسة.

## اختبارات القبول

- الوصول إلى `/admin/users/new` من قائمة المستخدمين.
- رفض الإرسال إذا كان الاسم أو البريد غير صالحين أو مكررين.
- عرض المؤسسة للقراءة فقط وحصر الأدوار بالمؤسسة.
- انتقال الخطوات الثلاث وعرض ملخص مراجعة قابل للفحص.
- عدم عرض النجاح إلا بعد نجاح `localStorage.setItem`.
- ظهور السجل بعد الانتقال إلى `/admin/users`؛ وعدم إرسال أي طلب API.
- منع الوصول عند تغيير الدور التجريبي، والتجاوب بعرض هاتف 390px.
- حالات تأكيد ترك النموذج والتخزين المعطّل.

**التحقق المتاح محليًا:** `npm run check:add-user`، و`node --test tests/contracts/*.test.mjs`، و`npm run lint` و`npm run build` بعد تثبيت الحزم. فحوص العقود وحدها لا تعني اختبار المتصفح.
