# الشاشة 20 — تفاصيل المستخدم (User Details)

**المسار:** `/admin/users/details?id=USR-001`  
**التقنية:** Next.js 15 App Router + React + TypeScript + Cairo/RTL + Bayan Design Tokens  
**الحالة:** نموذج واجهة أمامية تفاعلي؛ لا توجد مصادقة أو صلاحيات أو سجلات تدقيق فعلية من الخادم.

## الهدف وعلاقتها بمتطلبات بيان

تتيح الشاشة لمسؤول تقنية المعلومات المؤسسي استعراض المعلومات الأساسية لحساب ضمن مؤسسته، والدور وصلاحياته المقترحة، وحالة الحساب وآخر نشاط **افتراضي**، مع إجراءات تعديل بيانات المستخدم أو تغيير حالته داخل بيئة العرض فقط. تنتمي إلى مسار إدارة المستخدمين والأدوار (UC-04) وترتبط بالشاشتين `/admin/users` و`/admin/users/new`. يحتفظ المشروع بالتصميمين المرجعيين للمحادثة ولوحة الإدارة دون تغيير.

## المكونات

1. **رأس الصفحة:** مسار تنقل، العنوان، وتوضيح نطاق المؤسسة.
2. **بطاقة الهوية:** اسم، بريد تجريبي، معرّف USR، قسم، دور، حالة.
3. **بطاقات معلومات سريعة:** الحالة، الدور، تاريخ السجل، آخر نشاط توضيحي.
4. **تبويب البيانات الأساسية:** حقول تعريفية للقراءة فقط.
5. **تبويب الدور والصلاحيات:** صلاحيات واجهة وفق `lib/access/policy.ts`، وليست صلاحيات مؤسسية حقيقية.
6. **تبويب النشاط:** حالتا سجل توضيحيتان + إجراءات محلية تُسجل أثناء الجلسة؛ لا يتم تقديمها كسجل Audit حقيقي.
7. **نوافذ الإجراءات:** نموذج تعديل المستخدم وتأكيد التعطيل/التنشيط؛ رسائل نجاح/فشل.
8. **الحالات الطرفية:** رابط غير صالح، سجل غير موجود أو محذوف من المتصفح، دور ليس `it_admin`، فشل التخزين المحلي.

## تدفق البيانات التجريبي

- تعتمد الشاشات 18 و19 و20 كلها على `bayan.demo.users.v1` في `localStorage` وبنية `UserRecord` في `lib/user-management/users.ts`.
- تُستعاد السجلات عن طريق `restoreUserFixtures()` وتُرفض التركيبات الفاسدة وتعود البيانات الافتراضية.
- يتم تمرير `id` على شكل `USR-001`، مع دعم مرادف `user=USR-001`. لا يُقبل أي معرّف خارج التعبير `USR-\d{3,6}`.
- أزرار صفحة الإدارة تفتح التفاصيل الكاملة، وكذلك شاشة الإضافة بعد حفظ حساب وهمي. لا تُضاف بيانات شخصية فعلية.
- تعديل البيانات يمر عبر `validateUserDraft()` و`editUser()`، وتغيير الحالة يمر عبر `setUserStatus()`.
- لا تُعرض رسالة نجاح إلا بعد نجاح الكتابة إلى التخزين المحلي.

## قواعد الحماية التجريبية

- لا تعرض الواجهة محتوى الحساب إلا عند اختيار دور `it_admin` في محاكاة الواجهة.
- لا يمكن تغيير دور المسؤول الحالي `USR-003` أو تعطيل حسابه.
- يُرفض تعطيل آخر مسؤول تقنية معلومات نشط أو إزالة دوره.
- لا تمنح شاشة المؤسسة دور `platform_admin`.
- يجب تطبيق التحكم الحقيقي عند ربط FastAPI بعد المصادقة، والتحقق من نطاق `tenant_id` وRBAC والتدقيق في جميع عمليات قراءة وتعديل الحساب؛ **اختيار الدور في الواجهة لا يمثّل حماية أمنية.**

## عقود API المقترحة للمستقبل — غير منفذة

| Method | Path مقترح | الاستخدام |
|---|---|---|
| GET | `/api/v1/users/{id}` | بيانات المستخدم ضمن المؤسسة المصرح بها |
| PATCH | `/api/v1/users/{id}` | تحديث بيانات الحساب والدور حسب RBAC |
| PATCH | `/api/v1/users/{id}/status` | تعطيل/تنشيط مع منع آخر مسؤول |
| GET | `/api/v1/audit?entity=user&id={id}` | سجل تدقيق مخوّل القراءة |

الواجهات أعلاه مقترحات تكامل، **وليست وصفًا لمسارات موجودة حاليًا في FastAPI**. يجب عدم كشف الأسرار أو رموز الجلسات أو تفاصيل أمنية حساسة في واجهة الحساب.
