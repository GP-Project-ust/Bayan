# الشاشة 05 — مركز الإشعارات | Bayan

## الهدف والنطاق
صفحة مستقلة على `/notifications` لتجربة استعراض الإشعارات، البحث والتصفية، تغيير حالات القراءة، وعرض التفاصيل في درج جانبي. تُستعمل مكونات Design System وهوية «بيان» المعتمدة، مع **الاحتفاظ بواجهة المحادثة ولوحة الإدارة الأصليتين دون تغييرات بصرية**.

**الوضع:** Frontend تجريبي مع بيانات ثابتة؛ لا توجد خدمة إشعارات أو تسجيل دخول حقيقي أو إرسال أحداث حية من Backend.

## عناصر الشاشة
| القسم | السلوك |
|---|---|
| رأس الصفحة | عنوان، وصف، شارات توضيحية، أيقونة تنبيه |
| شريط التنبيه التجريبي | تنويه بأن الرسائل والتواريخ مجرد أمثلة |
| البطاقات الإحصائية | الإجمالي، غير المقروء، المهمة غير المقروءة، إشعارات التقارير |
| فلاتر القراءة | جميع الإشعارات، غير المقروءة، المقروءة |
| فئات الإشعارات | التقارير، المستندات، الأمان، الإدارة، النظام |
| البحث | في العنوان والوصف والتفاصيل والمصدر والفئة، مع تطبيع التشكيل العربي |
| قائمة الإشعارات | عنوان، وصف، شارة أهمية، فئة، مصدر، تاريخ، حالة قراءة، زر التفاصيل |
| درج التفاصيل | تفاصيل كاملة، بيانات وصفية، رابط داخلي لصفحة متصلة، إمكانية إعادة التمييز كغير مقروء |
| الإجراءات الجماعية | تمييز جميع الإشعارات كمقروءة، استعادة بيانات التجربة |
| الحالة الفارغة | رسالة واضحة وزر لمسح عوامل التصفية |
| أيقونة الجرس | `TopBar.tsx` يوجّه إلى `/notifications` مع الحفاظ على حجم الأيقونة وتنسيقها |

## البيانات التجريبية
- `lib/notifications/notifications.ts`: 11 رسالة بتاريخ توضيحي ثابت، خمس فئات، ثلاث درجات أولوية.
- **لا توجد طلبات fetch أو localStorage أو cookies**؛ تُحفظ حالة القراءة في React حتى إعادة تحميل الشاشة فقط.
- لا تتضمن البيانات أي بريد أو بيانات مستخدم حقيقية.
- جميع روابط التفاصيل داخل النظام وتستخدم مسارات ثابتة. وقد تكون وجهاتها شاشات تجريبية لم تُربط بعد بالخادم.

## التفاعل وسلوك القراءة
1. تظهر حالة جميع الإشعارات عند فتح الصفحة.
2. يطبّق البحث والتصنيف والتبويب بالتزامن على القائمة.
3. فتح التفاصيل يجعل الإشعار مقروءًا على مستوى الواجهة فقط.
4. يمكن تغيير حالة إشعار فردي إلى مقروء أو غير مقروء.
5. «تمييز الكل كمقروء» يحدّث الإحصائيات ويُعطّل عندما يصبح العدد صفرًا.
6. «استعادة التجربة» تعيد الإشعارات والفلاتر إلى القيم الابتدائية.
7. الأزرار والفلاتر والدرج قابلة للتحكم بلوحة المفاتيح، ويدعم درج التفاصيل Escape وتوجيه التركيز باستخدام مكون Design System.

## عقود API المقترحة للمرحلة المستقبلية — غير منفّذة
- `GET /api/v1/me/notifications?status=unread&category=reports` : استرجاع الإشعارات حسب المستخدم والمؤسسة.
- `PATCH /api/v1/me/notifications/{id}` : تحديث حالة قراءة إشعار يخص المستخدم الحالي.
- `POST /api/v1/me/notifications/mark-all-read` : تحديث جماعي بعد تحقق الخادم من هوية المستخدم.
- `GET /api/v1/me/notifications/stream` : بث أحداث جديدة عند اعتماد آلية push مناسبة؛ SSE اقتراح وليس ميزة موجودة.

لا يجوز تنفيذ هذه المسارات أو اعتبارها جاهزة قبل مراجعة عقد المصادقة والتفويض مع فريق Backend. يجب منع وصول المستخدم إلى إشعارات غيره والعزل بين المؤسسات على **الخادم**، وليس اعتماد فلترة الواجهة للحماية.

## اختبار القبول
1. شريط الجرس في المحادثة والإدارة والملف الشخصي ينتقل إلى `/notifications`.
2. جميع البيانات تحمل وصفًا صريحًا بأنها تجريبية، بدون ربط بالخادم.
3. حالة القراءة تبدأ بـ6 غير مقروءة من 11، وتُحدّث الإحصاءات مع التفاعل.
4. البحث والفلاتر المشتركة يعملان معًا وتُظهر الحالة الفارغة زر إعادة ضبط.
5. فتح الدرج يحدّث حالة الرسالة، مع توفر إغلاق بواسطة Escape وزر واضح.
6. التمييز الجماعي والإرجاع إلى الإعدادات الافتراضية يعملان دون طلب API.
7. لا تظهر تمريرات أفقية للصفحة عند 390/768/1280px، بينما يظل التصميم RTL.
8. الأسماء والألوان والخطوط مطابقة لنظام التصميم السابق، دون تغيير التصميمين المرجعيين.
9. تعمل روابط الوجهات التجريبية دون خروج عن نطاق المشروع.
10. التحقق من المسارات وملفات المراحل السابقة ومنع التعارض مع شاشة catch-all.

## التشغيل
```bash
npm install
npm run check:notifications
npm run lint
npm run build
npm run dev
# http://localhost:3000/notifications
```

> اختبارات Node البنيوية والمنطقية لا تمثل اختبارًا بصريًا أو أمنًا فعليًا. تحتاج اختبارات Playwright والبناء الكامل إلى حزم Next.js المتوفرة على جهاز التطوير.
