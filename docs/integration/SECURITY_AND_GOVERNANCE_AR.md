# الأمن والحوكمة والعزل وضوابط الاعتماد البشري

## 1. المصادقة والتفويض (Fail-Closed)

- لم يتضمن `dev` عند التكامل موفّر JWT/Session أو middleware موحداً يحقن هوية المستخدم. لذلك يقرأ dependency المسارات المحمية `Principal` من `request.state.principal` فقط؛ لا يستخرج الهوية أو العضوية أو الصلاحيات من جسم الطلب أو ترويسات العميل.
- يجب على موفّر الهوية الرسمي التحقق من الجلسة ثم حقن `Principal` يتضمن `user_id`, `tenant_id`, `roles`, `permissions`, `membership_id`, و`session_id`. لا يضيف هذا التكامل موفّر مصادقة مستقلاً.
- ترفض المسارات المحمية الطلب بـ`401` عند غياب `Principal` وبـ`403` عند غياب العضوية أو الصلاحية. تبقى مرفوضة افتراضياً في التطوير والإنتاج حتى يحقن middleware موثوق الهوية.
- يُشتق نطاق المؤسسة من سجلها المخزن ويُقارن بعضوية `Principal`. `X-Bayan-Tenant-ID` تحقق اتساق اختياري فقط؛ لا يمنح وصولاً. لا تُقرأ `X-Bayan-Permissions` ولا تُقبل كدليل صلاحية.
- تختبر مسارات API باستخدام `Principal` وهمي عبر FastAPI dependency override داخل الاختبارات فقط.

## 2. بوابات الاعتماد البشري ومنع الأتمتة المنفردة

- ترفض دالة `validate_human_actor` أي فاعل آلي (`ai`, `llm`, `bot`, `system`, `النظام`, `auto`, `automatic`).
- تُمنع مرحلة التفعيل (6) عبر `get_activation_readiness` ما لم تُعتمد المراحل 0–5 وتُغلق جميع التصعيدات المفتوحة.
- يتحقق `normalize_domain_analysis` من صحة كل مرجع جدول وعمود وعلاقة يقترحها AI ويرفض أي مرجع غير موجود في الكتالوج الفيزيائي.
- تتطلب إعادة تعيين أي مرحلة عبر `stage_reset.py` تأكيداً صريحاً (`confirm=true`) وسبباً ومشغلاً بشرياً مع تصفير جميع المراحل اللاحقة التابعة لها.

## 3. أمن البيانات في نماذج التضمين والذكاء الاصطناعي

- يقتصر الإرسال إلى `OfficialLLMStructuredGateway` (`app.llm.provider.get_llm`) و`OfficialEmbeddingService` (`app.core.qdrant.get_embeddings`) على البيانات الوصفية المعتمدة (أسماء، أوصاف، علاقات ومفاهيم) دون صفوف العملاء أو كلمات المرور أو استعلامات SQL التشغيلية.
