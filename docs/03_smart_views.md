# طبقة Smart Views — ابتكار المشروع

> لماذا يوجد بيان أصلاً؟ لأن السؤال العربي البسيط "كم رسوم الطالب المتأخرة؟"
> يترجم فوق مخطط Odoo الخام إلى استعلام شبه مستحيل — وSmart Views تحل هذا.

## المشكلة

مخطط Odoo/OpenEduCat مصمَّم للـ ERP لا للأسئلة الطبيعية:

1. **مئات الجداول**: فحص بيئة الاختبار أظهر 92 جدول `op_*` + 248 جدول Odoo نواة
2. **ميراث مفوَّض**: بيانات الطالب الحقيقية (الاسم، الهاتف، المدينة) ليست في
   `op_student` بل في `res_partner` عبر `partner_id` — النموذج لا يعرف ذلك
3. **علاقات ثنائية وسيطة**: ربط الطالب بمقرراته يمر بجداول مثل
   `op_student_course_op_subject_rel` — ثلاث طبقات قبل أي إجابة
4. **أعمدة تقنية لا معنى عربياً لها**: `create_uid`, `write_date`, `active`...

حتى نموذج لغوي قوي سيفشل نصف المرة في ربط هذه الشبكة — **وهناك هدف 90% لا يسمح بذلك**.

## الحل

مشاهد PostgreSQL بسيطة (VIEW) — جدول منطقي واحد لكل **مفهوم يفهمه المستخدم العربي**:

| المشهد | المفهوم لدى المستخدم | يخفي |
|--------|---------------------|------|
| `v_student_profile` | "الطالب" | ميراث res_partner + ربط البرنامج والدفعة |
| `v_fees_summary` | "رسوم الطالب" | تجميع دفعات + حساب المتأخرات |
| `v_exam_results` | "نتيجة الطالب" | كشوف العلامات + سلم التقديرات |
| `v_admission_stats` | "القبولات" | سجلات القبول + حالاتها (مقبول/مرفوض) |

**النتيجة**: النموذج يولّد SQL فوق 8-12 مشهداً بأعمدة عربية المعنى بدل 340 جدولاً
خاماً — قفزة مباشرة في الدقة، وprompt أصغر، وأسئلة أقل ضبابية.

## القواعد الملزمة

1. **التسمية**: `v_<المجال>_<الكيان>` — أمثلة: `v_student_profile`, `v_fees_summary`
2. **تعليق عربي إلزامي** لكل مشهد (`COMMENT ON VIEW`) — يدخل في الكتالوج الذي يقرؤه الـ prompt
3. **بلا منطق أعمال معقد**: JOIN وGROUP BY وتجميعات بسيطة فقط — الحسابات الذكية تبقى للوكلاء
4. **كل عمود له معنى عربي واضح** — لا أعمدة تقنية
5. **مصدر واحد للحقيقة**: ملفات SQL في `database/smart_views/` مرقّمة بالترتيب —
   لا مشاهد تُنشأ يدوياً في القاعدة وتضيع
6. **مراجعة PR**: أي مشهد جديد يراجعه قائد المشروع + صاحب البيانات (وليد)

## الكتالوج (وصف المشاهد للنموذج)

إلى جانب كل مشهد، يُبنى **كتالوج JSON** يصف المشاهد والأعمدة بالعربية —
وهو ما يرى النموذج فعلياً في الـ prompt (لا يرى المخطط الخام إطلاقاً):

```json
{
  "view": "v_student_profile",
  "description": "بيانات كل طالب: الهوية والبرنامج والدفعة",
  "columns": {
    "roll_number": "رقم القيد الجامعي (YU21xxxxx)",
    "program_name": "اسم البرنامج الأكاديمي",
    "batch_name": "دفعة القبول (سنة الالتحاق)"
  },
  "sample_questions": ["كم طالباً في كل برنامج؟", "أرقام هواتف طلاب تعز"]
}
```

## دورة الحياة

1. **Sprint 1**: أول دفعة (4-6 مشاهد) — طلاب ورسوم ونتائج وقبولات
2. **مع كل سؤال يفشل** في Golden Dataset: نسأل "هل غطاء المشاهد كافٍ؟" —
   ناقص؟ مشهد جديد أو أعمدة إضافية
3. **نهاية كل سبرنت**: مراجعة الكتالوج — حذف الأعمدة غير المستعملة (prompt أضيق = أدق وأسرع)
4. **قياس أثر كل دفعة**: الدقة قبل/بعد على نفس مجموعة الأسئلة — هذا يثبت الابتكار في المناقشة

## علاقة المشاهد بالأمان

- الوكلاء يستعملون `bayan_reader` — لا يملك صلاحية إنشاء/تغيير مشاهد
- المشاهد تُنشأ بصلاحية مدير Odoo من ملفات هذا المجلد فقط (قابلية إعادة إنتاج كاملة)
- عرض يكشف بيانات حساسة (هوية، هاتف) → تُوسَم في الكتالوج وتُقنَّع عند العرض
