# ADR-004: العقود المشتركة والحدود بين الوكلاء

**الحالة:** مقبول — نوفمبر 2026 (قبل انطلاق Sprint 1)
**السياق:** أربعة أعضاء سيعملون بالتوازي على الوكلاء والواجهات منذ اليوم الأول
من Sprint 1. أخطر ما يهدد ذلك هو أن يخترع كل عضو شكله الخاص للحالة المشتركة أو
لحدود الوكلاء فتتعارض فروعهم عند الدمج، أو أن يعدّل ملفًا مشتركًا فيكسر عمل
الآخرين بصمت.

**القرار:** تجميد العقود التالية كما هي في `main` اليوم، ولا يُعدَّل أي منها
إلا عبر PR يراجعه قائد المشروع حصرًا (تفرضه ملكية `CODEOWNERS` — أي `*` لمالك
واحد منذ PR التأسيس):

## 1) الحالة المشتركة `AgentState` (مصدر الحقيقة: `backend/app/agents/state.py`)

الحقول المعتمدة ومقصدها — أي وكيل جديد يقرأ ما يحتاجه ويكتب ما يخصه من هذه
الحقول فقط، ولا يضيف حقلًا جديدًا دون تعديل هذا العقد أولًا:

| الحقل | من يكتبه | المعنى |
|---|---|---|
| `question` | نقطة الدخول (API) | سؤال المستخدم العربي |
| `conversation_id` | نقطة الدخول (API) | معرّف المحادثة للذاكرة |
| `route` | `supervisor` | قرار التوجيه: `sql_agent` / `rag_agent` / `analyst_agent` / `reporter_agent` |
| `sql_query` | `sql_agent` | الاستعلام المولَّد (بعد التحقق) |
| `query_results` | `sql_agent` | الصفوف المنفَّذة (قائمة قواميس) |
| `rag_context` | `rag_agent` (reducer دمج) | المقاطع المسترجعة من Qdrant |
| `answer` | الوكيل الختامي في المسار | الإجابة النهائية المجمّعة |
| `agent_trace` | كل وكيل (reducer دمج) | أثر التنفيذ — بنية `AgentTraceEntry` في `app/schemas/chat.py` |
| `error` | أي وكيل عند الفشل | الخطأ — يشغّل فرع الإصلاح الذاتي |

## 2) حدود كل وكيل (مدخل ← مخرج)

كل وكيل دالة عقدة LangGraph موقّعة `(state) -> dict` تُرجع **فقط** الحقول
التي يملكها من الجدول أعلاه — لا يعيد بناء الحالة كاملة أبدًا:

- **supervisor**: يقرأ `question` (لاحقًا السياق) ← يكتب `route`.
- **sql_agent**: يقرأ `question` ← يكتب `sql_query` و`query_results` و`agent_trace` و`error`.
- **rag_agent**: يقرأ `question` ← يكتب `rag_context` و`agent_trace` و`error`.
- **analyst_agent**: يقرأ `query_results` ← يكتب `agent_trace` و`error` (لاحقًا `answer`).
- **reporter_agent**: يقرأ كل ما سبق ← يكتب `answer` و`agent_trace`.

بنية المخطط الحالية (`graph.py`) ثابتة حتى Sprint 3 حيث تتحول الحواف إلى
تدفق مركّب `sql → analyst → reporter` — إضافة الحواف المركّبة لا تغيّر
توقيعات العقد.

## 3) الملفات المشتركة — ملك القائد حصرًا

تعديل أي ملف من هذه القائمة في فرع عضو يعدّ إشارة خروجاً عن الخطة ويُرفض في
المراجعة: `state.py`، `events.py`، `graph.py`، `supervisor.py`،
`api/v1/router.py`، `schemas/chat.py`، `llm/provider.py`.

## 4) مبدأ mock-first (مرجع: ADR-002)

كل وكيل جديد يُطوَّر ويُختبر ضد `LLM_PROVIDER=mock` أولًا (ردود حتمية)، ثم
يُربط بالنموذج الحقيقي. اختبارات pytest لا تعتمد أبدًا على Ollama أو أي
اتصال خارجي — CI يعمل بـ `LLM_PROVIDER=mock` حصرًا.

## 5) سجل التدقيق — البنية المبكرة (تُفعَّل كاملة في Sprint 4)

كل حدث تدقيق يكتب السجل الموحد التالي (لأن كل وكيل سيحتاجه، يُثبَّت شكله
الآن ولا يُخترع لاحقًا): `timestamp` + `conversation_id` + `actor` (معرّف
المستخدم/دوره) + `agent` + `action` (نوع الفعل) + `query` (SQL أو استرجاع)
+ `rows_count` + `decision` (القرار/الرفض وسببه) + `agent_trace`.

## 6) golden dataset — مصدر الحقيقة للقياس

كل معيار قبول رقمي في أي مهمة يُشتق من `evaluation/README.md` (دقة التنفيذ
وزمن الاستجابة وفئات الأسئلة) و`evaluation/golden_dataset/questions.json`
هو المجموعة الوحيدة المعتمدة — ممنوع اختراع أرقام من خارجها.

**البدائل المرفوضة:** (أ) حرية كل عضو في تعريف حقول حالته — تضارب دمج
مضمون. (ب) جلسة «اتفاق شفهي» — لا يذكرها أحد بعد أسبوعين. (ج) تجميد كامل
لدرجة منع الإضافة — العقد يمنع الابتكار في الحدود لا داخلها: كل تعديل
مبنيّ على حاجة يمر بـ PR يراجعه القائد.

**النتائج:** كل عضو يعرف بالضبط ما يقرأ وما يكتب، والفروع تُدمج بلا تعارض
على المشتركات، والقياسات الرقمية لكل سبرنت تستند إلى مجموعة واحدة معتمدة.
